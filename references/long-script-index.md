# 长剧本两层建档

首次接收完整剧本时使用。仍通读全剧，保存原稿和版本；提速来自推迟未处理场次的详细执行规划，不是只看开头或用摘要替代原文。

## 第一层：首次全局索引

按场次/段落记录来源位置，紧凑保存：

- `characters`：人物ID、别名、身份和原文明示的稳定特征。
- `relationships`：人物关系及发生变化的场次；区分真实身份与当时已知身份。
- `scenes`：场次顺序、地点和原文范围，保留时间/空间跳转。
- `key_props`：推动剧情、跨场延续或需要辨识的道具，存在、归属、关键状态变化与来源位置。
- `timeline`：关键事件、因果、不可逆结果和时间锚点。
- `foreshadowing`：原文明示或上下文可确定的线索、揭示/回收位置，以及观众与人物分别何时知情；不另创伏笔。
- `unknowns`：影响执行但原文未确定的项目，保留未知，不提前补成事实。

这些列表可以为空，但必须来源于全剧扫描；空列表不能代表“还没读”。短描述和来源定位优先，不把每场逐句展开成动作台账。除上述七个列表，索引带 `source_version` 和 `source_sha256`，对应完整剧本当前原版基线。

```text
python -B scripts/project_state.py --project <项目目录> ingest --segment screenplay --input <完整剧本.txt>
python -B scripts/project_state.py --project <项目目录> story-index --segment screenplay --input <全局索引.json>
```

项目需已初始化。`ingest` 返回原稿版本及摘要；恢复时从状态读取并验证当前基线，不重新创建同名V0。索引工具只保存和校验版本，不自动做剧情理解。首次建档后继续遵循接收门禁，等待明确处理范围。

## 第二层：当前场次执行档案

用户指定片段后，读取本段原文、相关索引条目和必要前后场原文，再补齐当前场次的站位、朝向、临时服装/伤势、手部道具、进出场路径、动作进度和入口/出口。需要时回查更早的道具转移、关系变化或更晚的身份揭示，不能把未来信息提前泄露到镜头。

这些细节直接写入本段统一规划，不再建立一套平行的全剧详细台账。未处理场次保留索引层状态；不能把未建详细档案当作不存在的事件。

## 修订与资产输出

- 全剧来源发生修订时，工具将 `index_status` 标为 `stale`；保留旧索引供对照，只更新受影响场次及关系/道具/时间线/伏笔链。确认依赖范围后再登记新版本索引，不能只换摘要而不检查受影响内容。
- 片段有获准修订而尚未合回全剧时，在项目中记录片段版本与覆盖范围；本段采用已锁定片段来源，相关全剧索引需登记修订覆盖或标记待同步，不能用旧全剧原句覆盖获准的新片段。若原文/修订在跨场事实上冲突，先解决影响执行的项。
- 后续片段复用已验证索引，按需读取原文范围，不默认重新全文精细分析。
- 用户要求全剧资产列表时，仍提供完整人物、场景和相关道具清单，依 [asset-list-spec.md](asset-list-spec.md) 补齐概括描述。两层建档只推迟分镜执行细节，不缩减用户明确要求的资产交付。
- 不宣称首次索引已经完成全剧逐镜连续性质检；具体场次在进入分镜时完成语义检查。
