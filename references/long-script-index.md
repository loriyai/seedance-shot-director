# 长剧本两层建档

首次接收完整剧本时使用。仍需通读全剧、保存原稿和版本，但首次只建立轻量连续性索引；提速来自不为未处理场次提前写剧情摘要、动作台账、空间档案或逐镜规划，不是只看开头或用摘要替代原文。

## 阅读节奏与记录粒度

通读只针对用户给出的那一个剧本文件；不读同目录的其他文件，也不为对齐版本去翻旁侧材料。

- 分块读取，每块约 2000–3000 行（或 20–25k 字），整体控制在四到五次以内；不按 500–1000 行小块反复往返。
- 不做逐条精确行号定位：记录时按块起点加块内偏移写范围型 `ref`（如 `L1128-L1145`），需要时再回查一次；不为行号多次 grep 全文。
- 只收会影响后续分镜连续性的跨段事实：跨世身份链与别名冲突、原文明示的人名不稳定写法、关键道具归属与状态链、功法与真相主线、时空跳转锚点，以及阻断执行的 P0。
- 普通对白、局部动作、气氛、站位、服装、镜头设计，以及当场就能推断的细节一律不入索引。
- 建议上限（超出时合并或降级，不继续加条目）：人物 ≤15、关系 ≤8、场景 ≤10、关键道具 ≤8、时间线 ≤8、伏笔 ≤6。
- `characters` 的 `identity_changes` 只写跨世或身份揭示节点；`scenes` 只写时空边界；`timeline` 只写跨世与不可逆结果；`unknowns` 只留阻断执行的 P0。

## 第一层：轻量全剧索引

全剧只做一次顺序语义扫描，记录会影响后续分镜连续性的事实：身份与关系变化、场景边界、关键道具状态、关键时间锚、伏笔及真正的 P0。普通对白、局部动作、气氛、站位、服装细节和镜头设计留到当前片段处理。

索引统一使用 `lite-v1`。顶层必须包含当前原版基线、来源哈希、扫描覆盖范围、跨段审计状态和七个列表：

```json
{
  "index_schema": "lite-v1",
  "source_version": "V0",
  "source_sha256": "...",
  "coverage": [{"part_id": "full", "owned_ref": "L1-L9579"}],
  "review_status": "reviewed",
  "characters": [],
  "relationships": [],
  "scenes": [],
  "key_props": [],
  "timeline": [],
  "foreshadowing": [],
  "unknowns": []
}
```

同一项目只使用一种绝对来源定位格式；以下统一写作 `ref`，不得在分片间混用 `lines`、`range`、`source_lines` 或 `source_refs`。数组按首次来源位置排序。可选字段为空时省略，不写 `null`、空数组或解释性套话。七张表中的每条记录都必须有唯一 ID，最终前缀依次为人物 `C`、关系 `R`、场景 `S`、道具 `P`、时间 `T`、伏笔 `F`、未知 `U`。机械合并产生的最终记录另带 `merged_from` 保存分片临时 ID；跨段审计合并记录时取其并集并同步改写引用，直接单人整扫时可省略该字段。

### 最小字段

- `characters`：`id`、`names`、`first_ref`；只在确有内容时增加 `identity_changes[{scene,state,ref}]` 与 `stable[{fact,ref}]`。`scene` 必须引用本索引中的场景 ID。首次出现时已明确且会约束后续执行的身份写入 `identity_changes` 首项，后续揭示或阶段变化继续追加；`stable` 只收非身份类、跨场稳定且后续执行需要的原文明示特征。
- `relationships`：`id`、`parties` 与 `changes[{scene,state,ref}]`；`parties` 必须引用人物 ID，`scene` 必须引用场景 ID。只有观众、当事人或其他人物的知情时间不同且会影响表演时，才在对应变化项增加 `known`。
- `scenes`：仅含 `id`、`place`、`ref`；只有原文存在明确时间锚或同地叙事时间跳转时才增加 `time`。禁止写 `summary`、逐场剧情复述、动作细目或预设转场。
- `key_props`：`id`、`names` 与 `changes[{scene,state,ref}]`；`scene` 必须引用场景 ID。只收推动剧情、跨场延续或需要辨识的道具，`state` 用一句话写取得、归属、转移、损坏、启用或回收等关键变化。
- `timeline`：`id`、`scene`、`event`、`ref`；`scene` 必须引用场景 ID。只有确需跨场追踪时才增加 `anchor`、`cause` 或 `result`。普通场内事件不重复登记；`result` 只写不可逆或会约束后续执行的结果。
- `foreshadowing`：`id`、`clue` 与 `clue_ref`；已有回收时增加 `payoff`、`payoff_ref`，只有知情差影响表演时才增加 `knowledge_gap`。只记录原文明示或上下文可确定的线索，不另创伏笔。
- `unknowns`：仅含全剧读完后仍未解决且会阻断执行的 P0，字段为 `id`、`scene`、`type`、`issue`、`ref`、`blocks`。`scene` 必须引用场景 ID，`blocks` 是一句被阻断的具体执行判断；`type` 限于 `identity`、`relationship`、`speaker`、`goal`、`result`、`prop`、`space_time`。被后文解释的内容移入相应事实链或伏笔回收；P1、P2 和不影响执行的疑问不进入全局索引。

一条事实只在最适合的列表中保存，其他列表用人物、场次或道具 ID 关联，不重复改写。每项优先使用一句短事实和精确来源定位；若需要大段解释，应保留 `ref` 并推迟到当前片段精读，而不是扩大全局索引。完整人物造型、场景美术和普通物件描述不属于首次索引。

```text
python -B scripts/project_state.py --project <项目目录> ingest --segment screenplay --input <完整剧本.txt>
python -B scripts/project_state.py --project <项目目录> story-index --segment screenplay --input <全局索引.json>
```

项目需已初始化。`ingest` 返回原稿版本及摘要；恢复时从状态读取并验证当前基线，不重新创建同名 V0。索引工具只保存和校验版本，不自动做剧情理解。首次建档后继续遵循接收门禁，等待用户明确处理范围。

## 分片、合并与一次跨段审计

全剧较长时可以按完整场次边界分片并行扫描，但分片前必须锁定上述字段、纳入标准和绝对 `ref` 约定。分片同样遵守上节的粒度上限，不因为是一个分片就写全量细节。每个分片使用下列 envelope；`owned_ref` 是该分片唯一负责输出的连续绝对范围，`context_ref` 是可选的只读紧邻范围数组，最多各含一段前文与后文，不能从中输出记录。分片不写最终 `coverage` 或 `review_status`：

```json
{
  "index_schema": "lite-v1-part",
  "source_version": "V0",
  "source_sha256": "...",
  "part_id": "part_01",
  "owned_ref": "L1-L2500",
  "context_ref": ["L2501-L2550"],
  "characters": [],
  "relationships": [],
  "scenes": [],
  "key_props": [],
  "timeline": [],
  "foreshadowing": [],
  "unknowns": []
}
```

分片临时 ID 固定为 `<part_id>:<类别前缀><本地序号>`，例如 `part_01:C001` 与 `part_02:S003`。不在分片内部猜测跨世人物、别名或相似道具必为同一实体。单人整扫也使用 `part_id=full` 和同一字段契约。

伏笔线索与回收可能落在不同分片。看到线索的分片按正常 `clue` / `clue_ref` 记录；只看到回收而无法在本分片合法引用原线索时，允许写仅供待审合并使用的记录：`id`、`payoff`、`payoff_ref`、`clue_hint`，其中 `clue_hint` 只用一句话说明它可能回应的早期线索，不得伪造线索原文或越界填写 `clue_ref`。这种回收候选可以进入机械合并的 `pending` 文件，但跨段审计必须把它并入有依据的线索记录，或确认不构成伏笔后移除；最终 `reviewed` 索引不得残留仅回收候选。

先运行确定性工具做一次机械合并：校验字段和临时 ID，拼接七个列表，按绝对来源位置稳定排序，检查所有 `owned_ref` 无缺口且无重复归属，再按全剧顺序统一生成最终 ID，并同步改写已声明的人物与场景 ID 引用。任何重复 ID、悬空引用或异构字段都直接报错，不静默去重或猜测含义。最终 `coverage` 由各分片的 `part_id` 与 `owned_ref` 组成；`context_ref` 不进入覆盖范围。机械阶段不判断人物身份或剧情含义：

```text
python -B scripts/merge_story_index.py --source <完整剧本.txt> --source-version V0 --part <分片01.json> --part <分片02.json> --output <待审索引.json>
```

工具输出的候选固定为 `review_status=pending`，不能直接登记。跨段审计完成并把它改为 `reviewed` 后，`project_state.py story-index` 才接受；登记时会再次复用同一套结构、覆盖范围和来源 SHA 校验。

机械合并后只做一次跨段语义审计，同时完成：

1. 合并原文可确定的别名、身份阶段和同一关键道具；不确定者保持分离并列为 P0。
2. 串起身份、关系、关键道具状态和必要时间线变化。
3. 连接伏笔与回收，把分片中的仅回收候选并入有依据的线索记录并合并 `merged_from`；校准观众及人物的知情时间，防止未来信息提前进入当前镜头。
4. 删除已被后文解决的疑点，只留下真正阻断相关场次执行的 P0。
5. 检查分片边界是否遗漏场景、状态转移或因果，不进行第二轮全剧复述式复核。

完成后写入顶层 `review_status=reviewed`；`unknowns` 本身即为审计后仍存续的 P0 清单，不另存重复计数。复用 `ingest` 返回的来源 SHA-256；最终登记前只做一次 JSON 结构、覆盖范围和 `source_sha256` 校验。默认只保存最终索引，不生成分片报告、第二轮 P0 报告或全局建档长报告；用户明确要求时再输出。

## 第二层：当前片段执行档案

用户指定片段后，只精读本段原文、必要的前一场与后一场，以及本段人物、关系、道具、时间和伏笔涉及的索引条目。然后补齐当前片段的来源节拍、站位、朝向、临时服装与伤势、手部道具、进出场路径、动作进度、入口/出口和当时知情范围。

这些细节直接写入本段统一规划，不再建立一套平行的全剧详细台账。未处理场次继续保持轻量索引状态；不能把未建详细档案当作不存在的事件。

只有下列情况才沿 `ref` 定点回查更远原文：

- 当前片段涉及真实身份、假身份、转世、身份揭示或关键知情差。
- 当前片段埋设、揭示或回收伏笔。
- 当前片段依赖关键道具的取得、转移、损坏、启用或回收链。
- 索引与当前原文冲突，或相关 P0 阻断身份、说话人、目标、结果、道具归属或时空判断。

索引已经足以确定连续性时，不重复读取远处原文。允许读取后文来核实揭示或回收，但分镜只能使用该叙事时点观众与人物已经掌握的信息，不能把未来真相提前拍进表演、构图或素材选择。

当前片段默认做详细执行分析，但只扩大到必要依赖链。身份揭示、跨世/倒叙、伏笔回收、关键道具状态链、多场连续动作或伤势、索引冲突及 P0 会触发扩大精读范围；独立日常、因果闭合的普通对白或独立打斗维持“当前片段加必要相邻场”。只有用户明确要求篇章或全剧连续性质检时，才扩大到对应完整范围。

## 修订与资产输出

- 全剧来源发生修订时，工具将 `index_status` 标为 `stale`；保留旧索引供对照，只更新受影响场次及身份、关系、道具、时间线和伏笔链。确认依赖范围后再登记新版本索引，不能只换摘要而不检查受影响内容。
- 片段有获准修订而尚未合回全剧时，在项目中记录片段版本与覆盖范围；本段采用已锁定片段来源，相关全剧索引需登记修订覆盖或标记待同步，不能用旧全剧原句覆盖获准的新片段。若原文与修订在跨场事实上冲突，先解决影响执行的项。
- 后续片段复用已验证索引，按需读取原文范围，不默认重新全文精细分析。若当前精读发现全局索引遗漏，只局部修正受影响事实链，不重建全剧索引。
- 用户要求全剧资产列表时，仍提供完整人物、场景和相关道具清单，依 [asset-list-spec.md](asset-list-spec.md) 补齐概括描述。两层建档只推迟分镜执行细节，不缩减用户明确要求的资产交付。
- 不宣称首次轻量索引已经完成全剧逐镜连续性质检；具体片段在进入分镜时完成语义检查。
